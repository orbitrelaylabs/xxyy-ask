# 完整 Agent 客服系统 Goal

## Goal

把 `xxyy-ask` 从可信问答 MVP 完善为可运营、可治理、可复用的 Agent 客服系统，同时保持产品知识、链上只读、隐私、密钥和确定性发布边界。

## 已实现能力

### 会话与人工客服

- Web 使用高熵 `sessionId` 持久化脱敏后的多轮会话；Agent 只读取最近 12 条消息作为有界上下文，不依赖进程内隐式记忆。
- 用户必须明确点击“转人工”才创建工单；每个会话最多存在一个活动工单。
- 工单支持优先级、指派、处理中、等待用户、解决和关闭状态，并记录追加式审计事件。
- `/admin` 的客服工作台提供运营计数、工单队列、会话查看、人工回复和处理结论。
- Web 在转人工后轮询同一会话，只接收 `support_agent` 消息，不返回用户原文或 Agent 历史。

### 知识自学习与治理

- 自学习不是模型自行改权重。Telegram 群中的有界 reply 线程只有在验证知识作者身份后，才进入清洗、提取、冲突检查、确定性自动决策和隔离发布队列。
- Web 差评和无引用回答形成知识缺口信号，可在客服工作台检查；信号不会直接发布到正式知识库。
- Telegram 监听 `edited_message`。来源答案被编辑时，旧候选先被拒绝并写审计；已发布文档同时写持久 tombstone，检索立即排除旧 chunks，然后重新评估新内容。
- Telegram Bot API 不提供通用的群消息删除事件，因此实时 long polling 无法可靠感知删除。管理员可在客服工作台按群 ID / 消息 ID 确认删除并撤回；定期 Telegram Desktop 导出可作为发现删除的对账来源。

### 可复用集成

- `@xxyy/agent-sdk` 封装非流式问答、SSE 流式问答、反馈和显式转人工。
- `/api/v1/*` 是版本化外部 API，使用只存 SHA-256 哈希的 Bearer Key；未配置 `XXYY_AGENT_API_KEYS_JSON` 时失败关闭。
- `GET /api/v1/openapi.json` 提供 OpenAPI 3.1 契约。
- 原 `/api/chat*` 保留给同源 Web，避免破坏现有部署。

## 数据流

```text
Web / Telegram / SDK
        |
        v
LangGraph Agent -> Product RAG runtime -> pgvector 正式知识
        |
        +-> 脱敏会话 -> 显式转人工 -> 工单 -> 客服工作台 -> 人工回复
        |
        +-> 差评/低证据 -> 知识缺口检查队列

Telegram 管理员回复
        |
        v
身份验证 -> 清洗/提取 -> 自动治理 -> PublicationJob -> 独立 Worker -> pgvector
```

## 安全和运维约束

- 生产 API 进程不执行迁移或知识发布；先运行 `pnpm rag:migrate`，发布继续由独立 Worker 完成。
- 会话、反馈、工单主题和处理结论在写库前脱敏；用户 ID 只保存 SHA-256。
- 管理面继续使用独立 RBAC Token；外部 Agent API Key 与管理 Token 不复用。
- 公共客服不会自动读取账户、订单、钱包私有数据，也不会扩大浏览器链上数据边界。
- 当前运营指标是活跃会话、活动工单、未分配工单、等待用户工单和知识缺口计数。生产部署还应把结构化日志接入集中式 metrics/alerting，并制定数据库保留、删除、备份与恢复策略。

## 验收

- `pnpm rag:migrate` 能创建会话、消息、工单和审计表。
- Web 连续提问能使用服务端持久化上下文。
- 显式转人工创建幂等工单，客服工作台能指派、回复并解决。
- 差评/低证据只进入检查队列，不直接发布。
- Telegram 编辑和管理员确认的删除都能撤回候选；已发布来源通过持久 tombstone 从统计和检索中排除，不会静默保留旧答案。
- SDK 和 `/api/v1` 在有效 Key 下工作，无 Key 时失败关闭。
- `pnpm check` 通过。
